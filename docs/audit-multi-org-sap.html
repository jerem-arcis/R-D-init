00

Le constat central

À poser avant tout le reste

Aujourd'hui l'app fonctionne en 1 société × 4 usines (Bonloc 2886, Rivesaltes 2866, Agen 2847, Aire 2859). L'organisation commerciale SAP (VKORG) n'existe nulle part : ni dans le payload envoyé à SAP, ni dans Dataverse, ni dans les droits utilisateur. Elle est figée à l'intérieur du flux Power Automate — le fameux « champ fixe ».

Piège d'architecture à cadrer avec leur équipe SAP : « organisation commerciale » ≠ « division usine ». VKORG / VTWEG / SPART / BUKRS = dimension vente / commerciale — totalement absente de l'app. WERKS / division usine (2886, 2866…) = dimension logistique / site — la seule que l'app gère, sous le nom « division ».

Rendre l'app multi-org n'est donc pas étendre un existant : c'est introduire une dimension commerciale neuve et la brancher partout. La preuve est déjà dans le code : l'erreur SAP de démo MVKE-VKORG — « Organisation commerciale manquante : la vue vente n'a pas été créée » (src/dev/erreursSapDemo.js:85) — SAP réclame déjà ce que le payload ne fournit pas.

03

Tableau de bord — état & propositions

3 pages : Dashboard, Accueil (FL), DemandesEtude (DE/DS)

État actuel

  • Filtrage 100 % côté client (React state) ; aucun $filter OData.
  • projet.js:221-238 charge tous les projets puis filtre en JS → tient <1000 lignes, freeze à 5000+.
  • Présents : onglets statut, recherche texte, select usine (5 en dur), type demande, type DE/DS.
  • Absents : filtre org, demandeur, centre profit, plage de dates, tri colonne, persistance (query params), vues sauvegardées.

Propositions (par priorité)

  • Passer le filtrage côté serveur (OData $filter) — prérequis absolu du multi-org & chantier perf.
  • Filtre + scope « organisation » limité aux org autorisées du user, appliqué par défaut.
  • Filtres manquants : plage de dates, demandeur, centre profit/division ; persistance en query params.
  • Tri par colonne, vues sauvegardées par org/rôle, KPI recalculés par org.
04

Droits & scoping utilisateur

« n'afficher que les org autorisées » — le socle

État : aucun scoping

  • Identité = mock (base44Client.js:69-74, role:'admin' en dur).
  • Aucune table de liaison user↔org/division. ownerid/owningbusinessunit jamais lus.
  • Tous les dropdowns chargent tout (sapLists.js, optionSet.js).
  • Admin = gère uniquement les listes déroulantes + suivi créations SAP. Aucune gestion d'utilisateurs.

Cible

  • Identité réelle : brancher AuthContext sur le vrai user Power/Entra.
  • Référentiel : tables organisation, org↔division, user↔org.
  • Dropdowns filtrés par l'org sélectionnée, elle-même limitée aux org du user.
  • Admin étendu : gestion des org, des mappings user↔org, des règles par org.

06

Questions résiduelles qui chiffrent

Les 3 arbitrages qui déplacent encore l'estimation
  1. Granularité SAP — uniquement VKORG, ou aussi VTWEG (canal) et SPART (secteur) à transmettre ? Impacte la taille du payload et du référentiel.
  2. Divisions ↔ org — les usines sont-elles partagées entre organisations, ou partitionnées (chaque org a ses divisions) ? Impacte L1 + les dropdowns filtrés.
  3. Règles métier par org — les mappings de deRules.js (hiérarchie 22/27, centre profit…) sont-ils communs à toutes les org ou variables par org ? Si variables : L5 passe de M à L.
